## 1. 结论先行

第一轮交流的顺序是：抖音在某个 PTOAS 版本上测试 → 反馈问题（PTO 算子落后手写算子 26~50%，另一处口径写作劣化 3 倍） → **我方基于这些问题对 PTOAS 做了适配修改** → 麒麟真机实测性能提升约 30%（见 §2）。

所以本次交流的姿态不是解释性能差距，而是：

1. **主动交付**：你们反馈的问题已完成适配，麒麟真机自测约 +30%，请基于指定 commit 复测。
2. **争取复测承诺**：拿到他们用自己的模型和口径复测的窗口与原始数据。
3. **主动说明未覆盖项**（§2.3）：哪些反馈无法靠 PTOAS 适配解决、需要 pto-isa 或 bisheng 后端配合。不主动说，他们复测发现问题依旧会认为我方答复不实。

**最关键的一问仍是他们那个差距数字的口径**（§4.2）：+30% 之后我们到底追平没有，完全取决于原始 gap 是"慢 26%"还是"慢 50%"——前者基本追平甚至略优，后者仍落后约 15%。这个算术决定明天的话术是"已追平，请验收"还是"已大幅收敛，剩余差距共同归因"。

## 3. 从代码核对出的其他事实（作为提问依据）

### 3.1 片上存储规格差异大，容量已适配但 tile 策略未必

`lib/PTO/Transforms/PTOPlanMemory.cpp:54-61`、`:2160-2200`：

| 空间 | A3 | A5 | Kirin9030 |
| ---- | -- | -- | --------- |
| UB (VEC) | 192KB | 248KB | **128KB** |
| L1 (MAT) | 512KB | 512KB | 512KB |
| L0A / L0B | 64KB | 64KB | **32KB** |
| L0C (ACC) | 128KB | 256KB | **64KB** |

L0C 只有 A5 的四分之一。`PTOPlanMemory` 默认档是 a3，只有显式 `--pto-arch=kirin9030` 才切换（`:2189-2200`）——**所以复测时必须确认他们带了这个参数**，否则拿不到 `818d16d` 的收益。

注意区分两件事：`818d16d` 修的是**容量与对齐**，而 **tile 形状本身**由前端或用户决定。如果他们的算子 tile 是按数据中心尺寸选的，在 L0C 64KB 上仍会退化。这是 +30% 之后可能仍有剩余差距的头号候选原因（对应 §4.5）。

### 3.2 PTO 在端侧不是"直出 ISA"，与手写 cce 共用后端

端侧链路（[lite-side-kirin9030-usage-guide_zh.md](lite-side-kirin9030-usage-guide_zh.md) §1、§5）：

```text
Python 样例 → .pto → ptoas --pto-arch=kirin9030 → 调用 pto-isa 的 C++ → bisheng --cce-aicore-arch=dav-l311 → kernel .o
```

最终代码质量同时取决于 `pto-isa` 头文件实现和 bisheng 后端，而手写 cce 走同一个后端。两个后果：

1. 剩余差距不能笼统归给"PTO 编译器"，需分离 pto-isa 实现质量、bisheng 版本、以及 PTO 自身的 tiling/同步决策。这也是 §2.3 未覆盖项的判定依据。
2. 抖音"希望 PTO 开放 ISA 完备支持"这一诉求需要重新对齐：**PTO 是 tile 级虚拟 ISA，不是麒麟裸 ISA**，可能与他们想要的不是一个东西（对应 §6.13）。

### 3.3 PTOAS 内没有 Triton 前端

`README.md` 声明的前端是 **PyPTO / TileLang / CuTile**，全仓搜不到 Triton。抖音方案表里的"Triton 降级到 PTO"，其前端归属、代码位置、维护责任在本仓没有落点。这可能就是"进展慢"的真实原因——这条链没有 owner。

### 3.4 端侧支持尚未上主线

使用指南让用户从 `github.com/gtest-rgb/PTOAS` 的 `feature/kirin9030-arch-support` 取码，而 PTOAS 正式来源是 `gitcode.com/cann/pto-as`。这正是抖音"没看到发布时间和文档"的具体表现（对应 §6.14）。

### 3.5 端侧验证与 profiling 闭环尚未建立

`test/npu_validation/scripts/generate_testcase.py` 的 `--soc-version` 只覆盖 `Ascend910B1` / `Ascend950`（README §5.4）；profiling 文档只有 [msprof_op_simulator_usage_zh.md](msprof_op_simulator_usage_zh.md) 和 [no_npu_compile_only_guide_zh.md](no_npu_compile_only_guide_zh.md)。他们要的"整网 profiling"和"精度对比分析"在麒麟上目前没有现成流程（对应 §6.16）。

## 5. 第二梯队：把剩余差距归因到能落成 issue 的粒度

6. **这些算子在他们整网里的耗时占比**，以及 top-N 耗时算子和"最痛的三个"（paged attention、量化 matmul、rmsnorm、rope、KV cache 更新等）。占比决定单算子 +30% 能折算成多少整网收益；top-N 决定我们补齐的顺序（应按此排，而不是按语言特性覆盖度排）。
7. 剩余差距有没有 breakdown：搬运带宽（MTE）、cube 利用率、vector 空转、还是同步开销？有没有 profiling timeline 可以给我们。
8. **"不同芯片整网运行结果差异也很大"是精度差异还是性能差异？** 若为数值不一致，属正确性问题，优先级压过所有性能话题，当场索要具体 case。
9. **他们算子的 tile 形状是谁定的、有没有针对 128KB UB / 64KB L0C 人工调过**（§3.1）。若没调过，这部分差距我们可以自己验证复现。
10. 3bit / 4bit 量化算子的具体方案：per-group 还是 per-channel、zero-point 处理、权重 packing layout、解量化在哪一级做。直接决定 pto-isa 需要补哪些原子能力。
11. 融合边界谁负责（Triton 层手写大 kernel / PTO 编译器自动融合）；是否需要手工控制片上分配与多级流水——`--pto-level=level3` 可关闭 PlanMemory 与 InsertSync（README §5.1），若他们想自己控，这条路现成，值得当场确认是否是他们要的。
12. **"性能达标"的量化定义**：追平手写 cce，还是追平同规格安卓上的 QNN（他们给的 8Gen2 约 70 token/s、8Gen3 约 86 token/s）？可接受 gap 多少，按单算子还是整网 token/s 验收。没有这个数字，内部无法定义"做完了"。

## 6. 第三梯队：开放度、工具链、端侧硬约束

13. 让他们把"需要的硬件信息"按"缺了就没法优化"排序：指令语义、时延/吞吐表、流水与同步模型、片上存储层级与容量、bank conflict 规则。原话"底层 ISA 或一定抽象程度的 ISA"过于模糊，不排序无法判断能否提供。**并当场验证 PTO 这个 tile 级虚拟 ISA 是否就是他们要的"一定抽象程度的 ISA"**（§3.2），不要自行假设满足——这恰是 PTO 相对 AscendC 的差异点，他们对 AscendC 的核心抱怨是"拿不到底层信息、优化天花板低"。
14. 端侧支持何时上主线、以什么形式发布（§3.4）。**属 open list，不当场表态。**
15. 是否需要"一份代码跨 9020/9030"，还是允许 per-chip 调优。决定要不要在 PTO 层做代际抽象，成本差别很大。
16. profiling 要到什么粒度（算子级排序 / timeline / 单元利用率 / 指令级下钻）、在什么环境使用（真机、是否需要特殊权限）；精度分析是否需要逐层 dump 与参考实现比对、容差标准。以及在端侧闭环建好前（§3.5），他们最低可接受的替代方案。
17. 集成形态与端侧硬约束：kernel 二进制如何进入他们的推理引擎（预编译 `.o`/`.so`、静态注册、运行时 JIT）；包大小、启动时延、内存峰值是否有硬指标；功耗温升导致的降频。这些约束在数据中心侧不敏感，但会推翻一部分优化假设，也是"9020 比 9030 快 20%"的候选解释之一。
